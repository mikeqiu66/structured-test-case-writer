# structured-test-case-writer

一个面向测试设计场景的 OpenClaw Skill，用于基于需求文档、PRD、交互说明、版本说明等资料，按固定流程输出**结构化测试分析**与**正式测试用例**，并支持最终落地到飞书表格/飞书文档。

这个 skill 不是“直接生成一堆用例”的提示词集合，而是一套可复用的工作流，重点解决：
- 先分析还是先写
- 如何避免测试范围发散
- 如何补齐边界 / 异常 / 并发 / 兼容 / 稳定性
- 如何按正式格式输出测试用例
- 如何在飞书里稳定落地并校验

---

## 解决什么问题

适合下面这些场景：
- 根据需求文档 / PRD 编写测试用例
- 先做需求拆解，再整理测试点，再写正式用例
- 补测试点、问题澄清项、覆盖矩阵
- 输出标准测试用例表
- 将测试用例落到飞书表格 / 飞书文档
- 对复杂项目做结构化测试设计

特别适合这类项目：
- 有状态机 / 模式切换的项目
- 有页面切换 / 按键逻辑的项目
- 有时间窗口 / 调度逻辑的项目
- 有版本兼容逻辑的项目
- 有并发、中断恢复、优先级冲突的项目

## Skill 核心能力

### 1. 固定测试设计流程
默认要求按这个顺序执行：
1. 需求拆解
2. 测试点梳理
3. 问题澄清项
4. 覆盖矩阵（必要时）
5. 正式测试用例
6. 飞书落地与回读校验

### 2. 强制格式约束
正式测试用例默认遵循：
- 固定字段：`用例ID / 模块 / 用例标题 / 前置条件 / 操作步骤 / 预期结果 / 优先级 / 备注`
- 操作步骤与预期结果**一一对应**
- 统一使用 `#` 编号
- 空对应项也要保留 `#`

### 3. 飞书落地能力
内置飞书落地时的处理经验：
- 先小批量写入
- 分批处理，规避限流
- 写入后回读校验
- 遇到授权 / 限流时有默认处理策略

## 推荐使用方式

当你要让 OpenClaw 帮你写测试用例时，推荐直接用这些说法：
- 按之前流程写测试用例
- 根据这个 PRD 先拆需求，再写测试用例
- 先输出测试点和问题澄清项，再落正式用例
- 按标准测试用例表输出
- 补边界 / 异常 / 并发 / 兼容 / 稳定性用例
- 把结果写进飞书表格

这些表达更容易命中本 skill 的流程化能力，而不是退化成一次性生成文本。

## 最佳实践

### 1. 不要一上来就让 AI 直接写用例
先让它：
- 读资料
- 拆需求
- 梳理测试点
- 提问题澄清项

### 2. 复杂项目先补矩阵再写用例
遇到这类项目时，覆盖矩阵基本是必须的：
- 多版本
- 多状态
- 多模式
- 多时间窗口
- 多网络状态
- 多成员 / 多角色

### 3. 落飞书时不要默认一次性批量写入
尤其是正式用例较多时，推荐：
- 先试写小批量
- 再分批追加
- 每批回读确认

### 4. “内容生成完成”不等于“交付完成”
必须以：
- 已成功写入目标载体
- 格式符合要求
- 已回读确认
作为完成标准。

## 已沉淀出的典型踩坑

本 skill 来自真实项目复盘，已经明确规避这些常见问题：
- 未读资料就直接写用例
- 范围没有冻结，导致不断发散
- 没有覆盖矩阵，导致关键组合漏测
- 只提澄清项，不做闭环
- 步骤与预期不对应，无法执行回填
- 飞书授权 / 限流未预判
- 没有回读就宣称已完成

## 当前版本规则

本仓库后续统一按以下规则管理版本：
- 正式版本 tag 统一使用：`V4`、`V5`、`V6`、`V7` ...
- 新版本 tag 必须打在**当前主线最新提交**上
- 该提交必须**包含前一版本内容**，禁止把新版本 tag 打到不连续的历史节点上
- 若用户未特别说明，每次 push 默认同步升级一个版本号
- 当前已整理版本线：`V4`、`V5`、`V6`
- 后续默认从 `V7`、`V8` 继续递增
