# Weather Station 示例：从需求到正式测试用例的完整流程

本示例用于说明如何使用 `structured-test-case-writer` skill，完成一个复杂设备交互项目的测试设计与正式用例落地。

## 一、项目背景
本案例来自天气站项目新增迭代需求。目标不是直接生成零散测试点，而是走完整流程：
1. 读取需求资料
2. 做需求拆解
3. 梳理测试点
4. 输出问题澄清项
5. 编写正式测试用例
6. 写入飞书表格并校验

## 五、需求拆解时需要特别提取的规则
天气站不是普通单页功能，分析时必须重点提取这些规则：

### 1. 页面与按键逻辑
- 底部按键①循环主页/配置页
- 长按按键① `2s` 从配置页回主页
- 按键②进入日程
- 三日页中：
  - ②切回本人当日日程
  - ③切成员
  - ④切上午/下午

### 2. 调度与时间窗口逻辑
- 天气数据更新频率：`1h / 2h / 3h`
- 定时拉图：周期刷新
- `23:00~23:50` 预下载次日图片
- `0点后` 按天气数据更新情况决定刷缓存或重拉
- 主动拉图：长按顶部按键 `2s`

### 3. 兼容逻辑
- `7K` 已出货设备沿用旧方式
- `V9.26` App 对应旧逻辑
- 全面升级 `V20` 后，App 再热更文案

如果这些规则没有先抽出来，后面测试点一定不完整。

## 七、问题澄清项示例
在正式写用例前，应先识别不明确项，例如：
- 下载完成后刷新当前页，还是回原请求页
- 长按与单击边界阈值是否允许误差
- 三日视图退出后是否保留上次成员/分页状态
- 船运模式长按与恢复出厂长按的边界定义
- 旧固件 + 新 App / 新固件 + 旧 App 的兼容口径

这些问题如果不提前暴露，后面执行时一定返工。

## 九、正式格式要求（本案例实际踩坑总结）
本案例里，真正导致返工的，不是内容方向，而是格式规范。

最终确认的硬约束如下：
- 字段固定：`用例ID / 模块 / 用例标题 / 前置条件 / 操作步骤 / 预期结果 / 优先级 / 备注`

## 十、飞书落地过程中的实际问题
本案例中，落地飞书时遇到两个典型问题：

### 1. 授权问题
飞书写入需要用户完成授权，否则无法继续写表。

### 2. 限流问题
批量追加时出现：
- `too many request`

解决方式：
- 先写表头
- 再按小批量分批写入
- 每批写入后回读校验
- 不把“本地已生成文本”当成完成

## 十一、本案例沉淀出的通用结论
这个案例说明，复杂项目写测试用例时，必须坚持：
- 先读资料
- 先拆需求
- 先梳理测试点
- 先提澄清项
- 再写正式用例
- 再分批落地飞书
- 最后回读校验

否则很容易出现：
- 范围发散
- 关键组合漏测
- 预期口径不稳
- 格式返工
- 飞书写入失败却误以为已完成

## 十二、适合复用本案例的项目类型
以下类型项目，优先参考本案例：
- 有设备状态机的项目
- 有按键/页面切换逻辑的项目
- 有时间窗口/定时调度逻辑的项目
- 有版本兼容逻辑的项目
- 有并发/优先级/中断恢复逻辑的项目
- 最终需要正式落地到飞书文档/飞书表格的项目

## 十三、如何使用这个案例
当后续遇到类似项目时，可按以下方式复用：
1. 先按本案例方式识别核心模块
2. 先提取页面、按键、调度、兼容规则
3. 先整理测试点和澄清项
4. 再输出正式测试用例
5. 如果要飞书落地，默认分批写入并回读

这个案例不是模板替换，而是一个“完整工作流示例”。重点不只是写出用例，而是写出**能落地、能执行、能复用**的正式测试资产。
